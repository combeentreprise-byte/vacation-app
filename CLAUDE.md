# Project overview

A group vacation expense-splitting app (Splitwise-style): create a group, invite people, log shared expenses in any currency, see who owes whom, settle up. Built with Expo + React Native + TypeScript on the client, Supabase (Postgres + Auth + RLS) on the backend.

# Commands

- `npx expo start --web --port <unused port>` — run the dev server for verification (see Testing workflow below); `npm start` / `npm run ios` / `npm run android` for native.
- `npx tsc --noEmit` — typecheck. Run after every change.
- `npx eslint <changed files>` — lint. Run after every change (project-wide: `npm run lint`, which wraps `expo lint`).
- `npx supabase db query --linked "..."` or `--file supabase/schema.sql` — run SQL against the linked live Supabase project (already logged in / linked).
- No unit test suite is configured — verification is end-to-end against the real web build (see Testing workflow below), not a test runner.
- Path aliases: `@/*` → `src/*`, `@/assets/*` → `assets/*` (tsconfig.json).

# Architecture conventions — follow these for new features

- **Client state is a Context provider per domain** (`AuthProvider`, `ProfileProvider`, `GroupsProvider`, `LogsProvider`), each wrapping its own Supabase queries and mapping snake_case rows to a camelCase domain type (e.g. `mapGroup` in `use-groups.tsx`, `mapMember` in `use-group-members.tsx`), all mounted once in `src/app/_layout.tsx`. `useGroupMembers` is the one exception — a plain parametrized hook (`useGroupMembers(groupId)`) rather than a provider, since group membership is inherently scoped to whichever group is open rather than needed app-wide.
- **Any write that touches more than one table atomically goes through a `security definer` Postgres function in `supabase/schema.sql`, never sequential client-side inserts.** This is the app's central pattern (`create_group`, `create_log`, `update_log`, `settle_debt`, `leave_group`, `join_group`, `change_group_currency`, `delete_log`). The reason: a dropped connection between two separate client inserts can leave an orphaned/inconsistent row that RLS then hides from everyone, including its own creator. When adding a feature that writes to 2+ tables together, add a new RPC rather than two `.from(...)` calls.
- **Balances are always derived, never stored** — `src/utils/balances.ts`'s `calculateMemberBalances` computes everything from the log ledger, keyed by viewer perspective (positive = they owe you, negative = you owe them). The one stored number is `logs.converted_amount`, which exists purely so balance math doesn't require a live currency conversion on every read — it's always kept in terms of the group's *current* currency, rescaled atomically by `change_group_currency` whenever a group's currency changes. Never read `logs.amount` for balance math — that's the original entered amount/currency, for display only.
- **Group membership is soft-deleted** (`group_members.left_at`), never hard-deleted. `is_group_member()` checks `left_at is null`, which is what revokes a departed member's own access everywhere while leaving their historical logs/balances visible (grayed out) to everyone else. Rejoining reactivates the same row via `join_group`'s upsert rather than creating a new one. The one exception: if leaving drops a group to zero active members, `leave_group` deletes the group entirely (cascades via FK).
- **RLS is on for every table.** `is_group_member(group_id)` and `shares_group_with(user_id)` are `security definer` helper functions used throughout policies to avoid RLS-recursion issues. When a policy needs "am I active in this group," reuse `is_group_member`, don't reinvent it.
- **The currency list (`src/constants/currencies.ts`) is ISO 4217 filtered to what the exchange-rate API actually supports** — currently only `KPW` is excluded (open.er-api.com has no rate for it). If the API choice ever changes, re-diff the currency list against its supported codes before assuming coverage.
- **Confirm before anything irreversible.** There's no undo for a deleted log, a left/deleted group, or a settled debt from the UI — every such action gets an `Alert.alert` confirmation first.
- **Not-yet-built features route through `showComingSoon(feature)`** (`src/utils/coming-soon.ts`) rather than a silent no-op `onPress={() => {}}`.
- **OAuth sign-in shares its redirect/token-parsing plumbing with password recovery rather than pulling in native Apple/Google SDKs.** `src/utils/oauth.ts`'s `signInWithOAuthProvider(provider)` calls `supabase.auth.signInWithOAuth`; on web it lets Supabase do a full-page redirect that `src/app/auth-callback.tsx` catches on return, on native it opens `expo-web-browser`'s `WebBrowser.openAuthSessionAsync` and extracts the result directly — both paths end up calling `supabase.auth.setSession` with tokens pulled via the same `extractSessionTokensFromUrl` helper `reset-password.tsx` uses (see the `detectSessionInUrl` gotcha below).
- **Admin permissions are real, not client-side.** `group_members.is_admin` gates editing name/description/currency (`groups_update` RLS policy + `change_group_currency`'s own check use `is_group_admin`, mirroring `is_group_member`), promoting others (`promote_to_admin` RPC, admin-only), and kicking others (`kick_member` RPC, admin-only, self-kick rejected — use `leave_group` for that). The group creator is admin from `create_group`; if the only active admin leaves, `leave_group` auto-promotes the longest-standing remaining active member so a group can never end up with zero admins. Both `leave_group` and `kick_member` reset `is_admin = false` on departure, so a departed admin who later rejoins comes back as a plain member rather than silently keeping admin rights. UI gates (hiding "Edit group", graying "Promote to admin"/"Kick group member" — including for members who already left, so neither action gets a chance to hit the RPC's rejection path) are a courtesy on top of this — the RPC/RLS checks are what's actually authoritative.
- **Account deletion (`delete_account` RPC) is a real, permanent erasure, not a soft flag — but debts to/from a deleted account stay real, just anonymized.** It first leaves every group the caller is active in (reusing `leave_group`'s own admin hand-off / auto-delete-when-empty logic), then runs `delete from auth.users where id = auth.uid()` — allowed because the function is `security definer` and its owner has the necessary privileges over `auth.users` on this project; this cascades to the caller's `profiles` row (`on delete cascade`), the actual identity erasure. `groups.created_by`, `logs.paid_by`, `log_members.user_id`, and `group_members.user_id` are **all** nullable with `on delete set null` (not cascade) specifically so a deleted member's rows survive with the identity stripped rather than disappearing: a log's `shareCount` (`src/utils/balances.ts`) is computed from `log_members` row *count*, so cascading that row away would silently change every other member's historical split; cascading `group_members` away would make the person vanish from the Members tab instead of showing up as "Deleted user" the way a merely-departed member shows "Left group". Both `logs`/`log_members` and `group_members` needed a surrogate `id` primary key for this (their old PK was a composite including `user_id`, and a PK column can't be nullable). `calculateMemberBalances` and `useGroupMembers`' `mapMembers` both file every null-`user_id` reference under one shared `DELETED_USER_ID` sentinel (`src/utils/balances.ts`) rather than dropping it — the debt is still real even though the identity is gone, and if more than one deleted account has a debt in the same group, their amounts merge into that one bucket (an inherent limit of true erasure: two anonymized identities can't be told apart, so the balances/Members-tab UI collapses them into a single "Deleted user" line rather than showing several identical-looking ones). `MemberDetailOverlay`'s promote/kick rows are already disabled for it via the normal `!isActive` gating; the settle row needed its own explicit `targetIsDeleted` check since a `DELETED_USER_ID` "member" isn't a real uuid `settle_debt` could target.

# Known technical gotchas

- **`src/app/group/[id].tsx` is a ~1600-line single-file screen**, not split into `src/components/` the way the rest of the app is. `Avatar`, `AdminBadge`, `MemberRow`, `LogRow`, `MembersPane`, `LogsPane`, `MemberDetailOverlay`, `LogDetailOverlay`, and their formatting helpers (`formatLogHeadline`, `formatSettlementDetail`, `formatOriginalCurrencyNote`, ...) are all private functions/components living in this one file. Check here first before assuming a group-screen component has its own file elsewhere.
- **`usePopupAnimation` exists in two places that have diverged.** `src/hooks/use-popup-animation.ts` is the shared version (used by `group-actions-menu.tsx`; also exports `POPUP_CLOSE_DURATION_MS` and `popupScaleStyle`). `src/app/group/[id].tsx` has its own inline copy for the member/log detail popups, extended with an `onClosed` completion callback — fired on actual animation finish, not a guessed duration — so the log popup can hand off to the member popup only once it has verifiably finished closing, rather than risking two native `Modal`s presented at once (which can silently drop the second one on iOS, or leave a dead touch-blocking overlay on Android). Editing one copy does not affect the other.
- **`Alert.alert` and `Share.share` are no-ops on the web build.** Don't rely on Playwright clicking through a confirm dialog on web — verify that logic via direct `curl` calls to the Supabase RPC/REST API instead, or note that it needs on-device verification.
- **`src/lib/supabase.ts` disables session persistence when `typeof window === "undefined"`.** This is required — Expo Router pre-renders the web build in Node during dev/build, and the Supabase client's auto session-recovery on construction crashes the entire process without this guard.
- **`detectSessionInUrl` is deliberately `false`.** Password recovery links (`src/app/reset-password.tsx`) and OAuth redirects (`src/app/auth-callback.tsx`, via `src/utils/oauth.ts`) both parse tokens by hand instead (the auth flow is `implicit`, so tokens arrive as a URL fragment, not a query param) — don't assume Supabase auto-handles either.
- **`metro.config.js` adds `.mjs` to `resolver.sourceExts`** — required for `@supabase/supabase-js`'s dependency chain. Don't remove it.
- **Deep-linked screens need to work with no back-stack.** `src/utils/navigation.ts`'s `goBackOrToGroups()` falls back to the group list when `router.canGoBack()` is false — use it (not a bare `router.back()`) on any screen reachable via a deep link (invite links, password reset, etc).
- **`reset-password` and `auth-callback` are intentionally ungated routes** in `src/app/_layout.tsx` (outside both `Stack.Protected` blocks) since both can be reached before the client has established its own session yet. `auth-callback` is only ever hit on web — `signInWithOAuthProvider`'s native path resolves the redirect in memory via `WebBrowser.openAuthSessionAsync` without the app ever unmounting, so there's no screen transition to gate.

# Testing / verification workflow

- **The Supabase CLI is linked to the live project** (`supabase login` + `supabase link` already done). Use `npx supabase db query --linked "..."` or `--file supabase/schema.sql` to run SQL directly — no need to relay SQL for the user to paste into the dashboard.
- **Verify features end-to-end against the real web build**, not just by reading code: start `npx expo start --web --port <unused port>`, sign up throwaway test accounts via `curl` against the Auth API, drive the UI with a scratch Playwright script, and check results via direct `curl`/`supabase db query` calls against the database. Clean up test accounts/groups/rows after.
- Always run `npx tsc --noEmit` and `npx eslint <changed files>` after a change, before considering it done.

# Current known gaps (deliberately deferred, not oversights)

- No manual "demote admin" — an admin only loses the role by leaving/being kicked (which auto-demotes) or via the auto-promotion of someone else when they're the sole admin leaving.
- Account Settings' Password row and Danger Zone (delete account) are both real (`updatePassword`, `deleteAccount`); Notifications has a real settings UI but doesn't persist anywhere (local `useState` only, no backend column) — treat it as a mockup, not a saved preference. No push notifications or realtime updates exist. The Scan tab still shows a "coming soon" alert.
- No offline handling — failed writes mostly just `console.warn`, with no user-facing error or rollback of optimistic UI updates (see `use-profile.tsx`).
- Apple sign-in's button is present on the sign-in screen but intentionally inert — `handleOAuthPress` in `sign-in.tsx` routes it through `showComingSoon` since the Supabase Apple provider isn't configured yet. Google sign-in is fully wired and working.
