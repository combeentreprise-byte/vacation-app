# Project overview

A group vacation expense-splitting app (Splitwise-style): create a group, invite people, log shared expenses in any currency, see who owes whom, settle up. Built with Expo + React Native + TypeScript on the client, Supabase (Postgres + Auth + RLS) on the backend.

# Commands

- `npx expo start --web --port <unused port>` — run the dev server for verification (see Testing workflow below); `npm start` / `npm run ios` / `npm run android` for native.
- `npx tsc --noEmit` — typecheck. Run after every change.
- `npx eslint <changed files>` — lint. Run after every change (project-wide: `npm run lint`, which wraps `expo lint`).
- `npx supabase db query --linked "..."` or `--file supabase/schema.sql` — run SQL against the linked live Supabase project (already logged in / linked).
- No unit test suite is configured — verification is end-to-end against the real web build (see Testing workflow below), not a test runner.
- `npx supabase functions deploy scan-receipt` — deploy the receipt-scanning Edge Function (its `OPENAI_API_KEY` lives in Supabase function secrets, not the repo).
- `npx supabase functions deploy send-notifications --no-verify-jwt` — deploy the push sender. **Always with `--no-verify-jwt`**: pg_cron calls it without a user session, so without the flag the gateway rejects every call and nothing gets pushed. It checks its own shared secret instead (see the notifications note below).
- `node scripts/normalize-motives.js` — regenerate `assets/motives/` from `assets/motives-originals/` (see the motives note below).
- Path aliases: `@/*` → `src/*`, `@/assets/*` → `assets/*` (tsconfig.json).
- `README.md` is the untouched create-expo-app boilerplate (its `reset-project` script doesn't exist) — ignore it.

# Architecture conventions — follow these for new features

- **Client state is a Context provider per domain** (`AuthProvider`, `ProfileProvider`, `GroupsProvider`, `AccessProvider`, `LogsProvider`), each wrapping its own Supabase queries and mapping snake_case rows to a camelCase domain type (e.g. `mapGroup` in `use-groups.tsx`, `mapMember` in `use-group-members.tsx`), all mounted once in `src/app/_layout.tsx`. The exceptions are per-group data — `useGroupMembers(groupId)`, `useGroupEvents(groupId)`, `useGroupAccess(groupId)` — which are plain parametrized hooks rather than providers, since they're inherently scoped to whichever group is open rather than needed app-wide. Each screen using one gets its own copy, so a screen that another screen can change underneath it (e.g. the group screen or the entry form after buying a plan on `/paywall`) refetches when it's focused again — `useRefreshOnRefocus(refresh)`.
- **Any write that touches more than one table atomically goes through a `security definer` Postgres function in `supabase/schema.sql`, never sequential client-side inserts.** This is the app's central pattern (`create_group`, `create_log`, `update_log`, `settle_debt`, `leave_group`, `join_group`, `change_group_currency`, `delete_log`). The reason: a dropped connection between two separate client inserts can leave an orphaned/inconsistent row that RLS then hides from everyone, including its own creator. When adding a feature that writes to 2+ tables together, add a new RPC rather than two `.from(...)` calls.
- **Balances are always derived, never stored** — `src/utils/balances.ts`'s `calculateMemberBalances` computes everything from the log ledger, keyed by viewer perspective (positive = they owe you, negative = you owe them). The one stored number is `logs.converted_amount`, which exists purely so balance math doesn't require a live currency conversion on every read — it's always kept in terms of the group's *current* currency, rescaled atomically by `change_group_currency` whenever a group's currency changes. Never read `logs.amount` for balance math — that's the original entered amount/currency, for display only.
- **Group membership is soft-deleted** (`group_members.left_at`), never hard-deleted. `is_group_member()` checks `left_at is null`, which is what revokes a departed member's own access everywhere while leaving their historical logs/balances visible (grayed out) to everyone else. Rejoining reactivates the same row via `join_group`'s upsert rather than creating a new one. A group holds at most 15 active members (`join_group` refuses the 16th; `GROUP_MEMBER_LIMIT` in `src/constants/limits.ts`, matching the biggest group plan) — members who left don't count. The one exception: if leaving drops a group to zero active members, `leave_group` deletes the group entirely (cascades via FK).
- **RLS is on for every table.** `is_group_member(group_id)` and `shares_group_with(user_id)` are `security definer` helper functions used throughout policies to avoid RLS-recursion issues. When a policy needs "am I active in this group," reuse `is_group_member`, don't reinvent it.
- **The currency list (`src/constants/currencies.ts`) is ISO 4217 filtered to what the exchange-rate API actually supports** — currently only `KPW` is excluded (open.er-api.com has no rate for it). If the API choice ever changes, re-diff the currency list against its supported codes before assuming coverage.
- **Confirm before anything irreversible.** There's no undo for a deleted log, a left/deleted group, or a settled debt from the UI — every such action gets a confirmation first — usually `Alert.alert`, but leaving a group (`GroupActionsMenu`), deleting a log (`LogEntryActions` in `group/[id].tsx`), and the member popup's promote / kick / settle rows (`MemberActionRow` in `MemberDetailOverlay`) instead morph their own UI in place into a Cancel / confirm pair. `ConfirmationBody` in `leave-group-confirmation.tsx` is the shared message + buttons block for these.
- **Offline support is deliberately narrow: new log entries and your own name/profile picture work offline; everything else is online-only.** Every provider (plus `useGroupMembers` and exchange rates) keeps an on-device copy of its last server fetch (`src/utils/offline-storage.ts`, AsyncStorage keyed `offline:<userId>:...` so accounts never see each other's data) and shows it first on load, so the app is usable with no connection. Offline-capable writes go through a saved queue rather than straight to the server — *always*, online or not, so there's one code path: `LogsProvider`'s `PendingLog` queue (FIFO, flushed one `create_log` at a time) and `ProfileProvider`'s single pending name + pending avatar slot (native copies the picked image into `Paths.document/offline/<userId>/`, web stores a data URL). Pending items are merged into what the UI shows (`isPending` logs get a "Waiting to sync" marker and already count in balances) and flushed by `useSyncTriggers` (NetInfo reconnect, app foreground, `TOKEN_REFRESHED`, and every 30s while anything's queued). Retryable failures (status 0/401/408/429/5xx — `src/utils/network.ts`) leave the item queued; a real server rejection drops it and shows an alert — except a paywall rejection (`error.code === "PT402"`), which *holds* the entry instead (`heldForUnlock`: "Needs an unlock" marker, left out of balances, retried on every sync trigger but without keeping the 30s timer alive; see the plans note below). `create_log` takes a client-generated `p_id` (idempotent retries — a lost response can't double-insert an expense), `p_created_at` (when it was entered, clamped to `now()`), and `p_converted_currency` (rescaled server-side if the group's currency changed while it sat in the queue). Editing/deleting a still-pending entry just edits the queue. Signing out wipes the user's device data (warning first if anything's unsynced). If you make another write offline-capable, follow the same shape: client id + idempotent RPC, queued in the owning provider, retryable-vs-rejected classification.
- **Receipt scanning goes through the `scan-receipt` Supabase Edge Function** (`supabase/functions/scan-receipt/index.ts`), which proxies a photo to OpenAI `gpt-4o-mini` with a structured-output schema and returns `{ amount, currency }` (both nullable — the client falls back to manual entry). It relies on the gateway's default `verify_jwt` for auth and never touches the database. `ReceiptScanner` (`src/components/receipt-scanner.tsx`) is used both inside `add-entry.tsx` and by the Scan tab, which has no group yet so it routes through `scan-pick-group.tsx` with `prefillAmount`/`prefillCurrency` params before reaching Add entry.
- **Notifications are written by the database, in the same transaction as the change they're about, and pushed by a cron-driven Edge Function.** The full list with wording (and who gets what) is `docs/notifications.md` — keep it in sync with the SQL. Every notification goes through the internal `notify()` in `schema.sql`, which skips the person who did it (except `'always'` ones like a password change), people no longer active in the group, and anyone who turned its category off (`notification_settings`, read by `notification_category_on`; the plan categories also need plans to be visible to them). Where they come from: everything recorded in `group_events` is handled by one trigger (`notify_group_event`) rather than code in each RPC; entries/settle-ups by `notify_entry_added`/`notify_entry_changed`/`notify_entry_deleted`/`notify_settlement`, called from `create_log`/`update_log`/`delete_log`/`settle_debt`; group edits by a trigger on `groups`; plan changes inside `reschedule_plan`/`upgrade_plan`; free entries running low inside `check_entry_access`; a password change by a trigger on `auth.users`; and every time-based reminder (pass/subscription ending or renewing, pass not set up, free seats before a start, a member's unlock ending, a later-starting pass starting) by `send_scheduled_notifications()`, run every 10 minutes by pg_cron — each sent once per person via `dedupe_key`. Dates in the text use the recipient's time zone (`notification_settings.time_zone`, saved by the app). Entries and joins from the same person/group are merged while unsent (`merge_key`, held back 2 minutes). Sending: pg_cron runs `trigger_notification_sender()` every minute, which (only when something is due) calls the `send-notifications` Edge Function via pg_net with a shared secret (`NOTIFICATIONS_CRON_SECRET` in function secrets = `notifications_cron_secret` in Vault, next to `project_url` — neither in the repo); the function claims due rows (`claim_due_notifications`, marking them sent), posts them to Expo's push API for each of the person's `push_tokens`, and drops tokens Expo reports as `DeviceNotRegistered`. Client: `NotificationsProvider` (`use-notifications.tsx`) loads/saves the settings (switches defined in `src/constants/notifications.ts`, mirrored by `notification_category_on`'s defaults), registers the phone (`src/utils/push-notifications.ts`, via `register_push_token`, on every signed-in launch; `signOut` unregisters it first), and `useOpenTappedNotifications` in `_layout.tsx` opens a tapped notification's `url`. To add one: write it with `notify()` where the change happens, give it a category, and add it to `docs/notifications.md`.
- **Group "motives" are SVG illustrations imported as components** (`react-native-svg-transformer`, wired in `metro.config.js`; list in `src/utils/hero-motive.ts`). `svgr.config.js` rewrites `#000000` → `currentColor` and `#FFFFFF` → a `holeColor` prop so `HeroMotive` can recolor any motive at runtime. VTracer-traced files are generated by `scripts/normalize-motives.js` from `assets/motives-originals/` — edit the originals and re-run it, never hand-edit `assets/motives/`.
- **Anything that loads shows a skeleton, never a spinner, a blank screen, or an empty state that isn't true yet** ("No entries yet", "No plan yet", "Your Name" before the data has arrived). `src/components/skeleton.tsx` has the primitives (`Skeleton`, `SkeletonText` sized from a font size so the real text drops in without shifting anything, `SkeletonGroup` around a whole placeholder layout for one screen-reader "Loading", and `SkeletonImage`, used by `Avatar`/`GroupHero` for remote pictures); `src/components/screen-skeletons.tsx` has the layouts several screens share (group list, whole group screen, member/log/plan rows). A screen's own one-off skeleton lives in its file. Lay a skeleton out like what replaces it — same paddings and sizes; numbers both need go in `src/constants/layout.ts`. Gate on the data's `isLoaded`: every provider and per-group hook keys it to the account / group it loaded for (`loadedFor`), so it reads false again while a newly signed-in account's or a newly found group's data loads. Spinners are only for a button's own in-progress action (submitting, scanning, cropping). The app launch holds the native splash screen (`_layout.tsx`) until the stored session has been read.
- **The app asks for a store rating on its own, never from a button** (`src/utils/review-prompt.ts`, `expo-store-review`'s `requestReview`, the OS's own popup). `LogsProvider` calls it after a successful settle-up (`onDebtSettled`) and after entries sync (`onEntriesSynced`, which counts them; it asks from the 10th on, never when the same sync had a rejected or held entry). It holds back in an account's first 3 days, for 120 days after asking, within a day of the paywall opening on its own (`lastPaywallNudgeAt`), on web, and in TestFlight (`isAvailableAsync` is false there; Apple also shows the popup at most 3 times a year and never says whether it did). Its record is kept on the device (`offline:<userId>:review-prompt`).
- **Not-yet-built features route through `showComingSoon(feature)`** (`src/utils/coming-soon.ts`) rather than a silent no-op `onPress={() => {}}`.
- **OAuth sign-in shares its redirect/token-parsing plumbing with password recovery rather than pulling in native Apple/Google SDKs.** `src/utils/oauth.ts`'s `signInWithOAuthProvider(provider)` calls `supabase.auth.signInWithOAuth`; on web it lets Supabase do a full-page redirect that `src/app/auth-callback.tsx` catches on return, on native it opens `expo-web-browser`'s `WebBrowser.openAuthSessionAsync` and extracts the result directly — both paths end up calling `supabase.auth.setSession` with tokens pulled via the same `extractSessionTokensFromUrl` helper `reset-password.tsx` uses (see the `detectSessionInUrl` gotcha below).
- **Admin permissions are real, not client-side.** `group_members.is_admin` gates editing name/description/currency (`groups_update` RLS policy + `change_group_currency`'s own check use `is_group_admin`, mirroring `is_group_member`), promoting others (`promote_to_admin` RPC, admin-only), and kicking others (`kick_member` RPC, admin-only, self-kick rejected — use `leave_group` for that). The group creator is admin from `create_group`; if the only active admin leaves, `leave_group` auto-promotes the longest-standing remaining active member so a group can never end up with zero admins. Both `leave_group` and `kick_member` reset `is_admin = false` on departure, so a departed admin who later rejoins comes back as a plain member rather than silently keeping admin rights. UI gates (hiding "Edit group", graying "Promote to admin"/"Kick group member" — including for members who already left, so neither action gets a chance to hit the RPC's rejection path) are a courtesy on top of this — the RPC/RLS checks are what's actually authoritative. `group_members` is select-only for clients (no insert/update/delete grants or policies) — every membership change goes through these RPCs.
- **Each group can have one sponsor (`group_members.is_sponsor`), a role above admin.** Whoever sets up a group pass for the group becomes it (`set_up_plan`; anyone holding it from an earlier plan stays an admin), and it's kept after the plan ends. A sponsor is always an admin too (`group_members_sponsor_is_admin` check), so every admin check covers them; on top of that `kick_member` refuses them, only they can demote admins (`demote_admin`, recording `admin_demoted`; never the sponsor themselves), and they're who hands out the group plan's seats (`can_manage_plan` — the plan's buyer only while they still hold the role; admins only if the group has no sponsor). When the sponsor leaves (or deletes their account), `leave_group` hands the role to the longest-standing remaining admin, else the longest-standing member (made admin too), recording `sponsor_handed_over`; the leaver gets `left_as_sponsor` and is never picked by a later hand-off (rejoining keeps the old `joined_at`, which would otherwise put them first in line) — only setting up a new pass makes them sponsor again. If everyone left has given the role up before, the group goes without a sponsor. The leave confirmation warns a sponsor they won't get it back (`isSponsor` on `LeaveGroupConfirmationBody`, from `useGroups`' `Group.isSponsor` on the group list and `GroupMember.isSponsor` on the group screen). The UI shows the `SponsorBadge` from `GroupMember.isSponsor` (not the plan's buyer), turns the member popup's promote row into "Demote admin" for the sponsor, and grays out "Promote"/"Kick" on the sponsor. **The duty to hold a seat goes with the role, not the purchase**: on a group pass that hasn't started, whoever is the group's sponsor *now* needs a seat unless something else unlocks them at the start — `reschedule_plan` and `remove_plan_seat` check the current sponsor (not `plans.sponsor_id`), and so do `/group-plan` (which protects their seat and tells them when they're missing one) and `/plan-setup`'s reschedule warning. When the sponsor leaves before the start, their seat is freed like anyone's (see the plans note below) and the new sponsor is given one (`plan_seat_given`) unless they're already seated, otherwise covered, or the pass is full — then they have to take a seat back from someone and give it to themselves.
- **Membership history lives in its own `group_events` table, never in `logs`.** Group created / member joined / left / kicked / promoted / auto-promoted / demoted / sponsor handed over / plan started / seat given / seat taken back are each recorded by the RPC that makes the change (`create_group`, `join_group`, `leave_group`, `kick_member`, `promote_to_admin`, `demote_admin`, `set_up_plan`, `assign_plan_seats`, `remove_plan_seat`), in the same transaction. Clients get select-only access (grants revoked beyond `select`, no write policies). Those RPCs make the state change conditional (`update ... where left_at is null` / `is_admin = false`, then `if found`), so a repeat or concurrent call can't record a duplicate event. `useGroupEvents(groupId)` (a plain hook, like `useGroupMembers`) feeds `LogsPane` in `group/[id].tsx`, which merges events and logs into one newest-first list and renders events as a one-line tinted `EventRow` card (colors are `Colors.eventSurface`/`eventBorder`/`eventText`). The two plan kinds are the exception: they carry a `details` jsonb snapshot of the plan at that moment (seat count, start, end, starting seat holders / seats used), written by `set_up_plan`/`assign_plan_seats`, and render as a bigger `PlanEventCard` ("X bought a 4-seat plan…, expires in N days, on d.m.yyyy" — or "starts in N days…" for a pass set up to start later — "who has seats, seats left") — the start and expiry follow the group's plan live when it's the same plan, everything else is history. A kind unknown to the client build is skipped. To add a kind: extend `group_events_kind_check` in `schema.sql`, `GROUP_EVENT_KINDS` in `use-group-events.ts`, and `formatEventText`/`EVENT_ICONS` in `group/[id].tsx`. There's no history before this shipped (2026-09-30).
- **Account deletion (`delete_account` RPC) is a real, permanent erasure, not a soft flag — but debts to/from a deleted account stay real, just anonymized.** It first leaves every group the caller is active in (reusing `leave_group`'s own admin hand-off / auto-delete-when-empty logic), then runs `delete from auth.users where id = auth.uid()` — allowed because the function is `security definer` and its owner has the necessary privileges over `auth.users` on this project; this cascades to the caller's `profiles` row (`on delete cascade`), the actual identity erasure. `groups.created_by`, `logs.paid_by`, `log_members.user_id`, and `group_members.user_id` are **all** nullable with `on delete set null` (not cascade) specifically so a deleted member's rows survive with the identity stripped rather than disappearing: a log's `shareCount` (`src/utils/balances.ts`) is computed from `log_members` row *count*, so cascading that row away would silently change every other member's historical split; cascading `group_members` away would make the person vanish from the Members tab instead of showing up as "Deleted user" the way a merely-departed member shows "Left group". Both `logs`/`log_members` and `group_members` needed a surrogate `id` primary key for this (their old PK was a composite including `user_id`, and a PK column can't be nullable). `calculateMemberBalances` and `useGroupMembers`' `mapMembers` both file every null-`user_id` reference under one shared `DELETED_USER_ID` sentinel (`src/utils/balances.ts`) rather than dropping it — the debt is still real even though the identity is gone, and if more than one deleted account has a debt in the same group, their amounts merge into that one bucket (an inherent limit of true erasure: two anonymized identities can't be told apart, so the balances/Members-tab UI collapses them into a single "Deleted user" line rather than showing several identical-looking ones). `MemberDetailOverlay`'s promote/kick rows are already disabled for it via the normal `!isActive` gating; the settle row needed its own explicit `targetIsDeleted` check since a `DELETED_USER_ID` "member" isn't a real uuid `settle_debt` could target.
- **First-run onboarding happens before sign-up, and signing up is its last step.** `src/app/onboarding/` (name, required, + optional photo → first group, skippable → sign-up) runs entirely signed out. Everything is held in `OnboardingProvider`'s draft (`use-onboarding.tsx`), kept on the device (`offline:shared:onboarding-draft`, photos under `Paths.document/offline/onboarding/`) since web's Google sign-in leaves the app via a full-page redirect. The draft is saved to an account only when a session appears *while `draft.isSigningUp` is set*: the last step sets it right before signing up, and the sign-in screen clears it on focus, so signing in to an existing account discards leftover onboarding instead of writing it over that account. Saving reuses the normal paths (`ProfileProvider`'s queue for name/picture, `addGroup` + `uploadGroupPhoto` for the group), then opens the new group with `invite=1`, which makes the group screen open the invite share sheet once its push transition ends (`transitionEnd` is only emitted by the native stack, so this does nothing on web). New accounts can only be created there (the sign-in screen's "Sign up" link goes to onboarding), so every email account has a real name rather than the `'Your Name'` default. Where a signed-out user lands depends on `offline:shared:has-signed-in` (set the first time any account signs in on the device): onboarding on a fresh install, the sign-in screen otherwise. This is done purely by the order of the two screens inside `_layout.tsx`'s signed-out `Stack.Protected`, since a false guard redirects to the first available screen. The group step reuses `GroupForm` (`src/components/group-form.tsx`), which `new-group.tsx` is now a thin create/edit wrapper around; `AuthForm` (`src/components/auth-form.tsx`) is likewise shared by the sign-in screen and the sign-up step.
- **Adding or editing an entry is behind a paywall; nothing else is.** The rule lives in `check_entry_access` (`schema.sql`), called by `create_log` and `update_log`: the caller (always the payer) and every non-null member of the split must be unlocked, or the entry uses up one of the group's free entries, and once those are gone it raises SQLSTATE `PT402` (PostgREST answers HTTP 402). Viewing, settling up (`settle_debt`) and deleting your own entries (`delete_log`) are never gated — settling has to keep working after everyone's plan has ended. Details:
  - **Free entries** are one pool per group (since 2026-10-03; briefly 5 per person per group before): each group shares `billing_settings.free_entries_per_group` (15), usable by anyone on entries split with anyone. Once they're gone, locked people are grayed out in the entry form and only unlocked people can add entries, among themselves. One is used by any add or edit that wouldn't otherwise be allowed (edits count too), counted in `free_entry_usage` (keyed by group) — a lifetime counter with no client access, so deleting an entry never hands one back. `get_group_access`'s `free_entries_left` is the group's count; the client subtracts this device's still-queued entries in the group from it (`freeEntriesLeft` in `utils/access.ts`), a pessimistic guess since a queued entry with everyone unlocked won't use one — but optimistic about other members, whose phones use the same pool. The entry form shows the count whenever the entry would use one, including to an unlocked person who picks a locked one.
  - **Unlocked** means holding a seat on a running **plan** (`plans`/`plan_seats`), bought by its *sponsor* (the UI's name for the one who pays). A plan is a Trip Pass (1/2 weeks, one-time; *Just me* or a group size) or a subscription (monthly/yearly, **always *Just me***, starting the moment it's bought). *Just me* is `group_id` null, one seat, always the sponsor's; a group plan has 4/8/15 seats handed out to that group's active members, and a group has **at most one plan that hasn't ended** (running or still to start). **A Trip Pass is bought before it's set up**: `test_purchase_plan`/`create_plan` make it with `starts_at`/`ends_at` null and no seats (it keeps its length in `plans.duration`) — it doesn't count down until its sponsor sets it up with `set_up_plan` (group for a group size, start "right away" or a day up to a year out, first seat holders), and `reschedule_plan` moves the start until it begins (sponsor for *Just me*, `can_manage_plan` for a group pass). Seats on a pass that hasn't started don't unlock anyone yet — `unlocked_until` and the rest only count plans with `starts_at <= now()`. A seat unlocks its holder in *every* group. Until a pass starts, whoever manages it can take a seat back (`remove_plan_seat`, recording `plan_seat_removed`) and give it to someone else — except the group sponsor's own (whoever holds the role now — see the sponsor note above) while nothing else unlocks them at the start (an unlock that ends before the pass does only gets a warning). **Leaving or being removed from a group before its pass starts takes your seat back automatically** (`free_pending_plan_seat`, internal, called by `leave_group` and `kick_member`; `plan_seat_removed` with actor = the leaver — shown as "gave up their seat" — or the admin who removed them), so seats aren't held for people who may never come back; rejoining doesn't restore it, but whoever manages the pass can give it back (or to someone else), before or after the start. The leave confirmation warns about it (`seatStartsAt` on `LeaveGroupConfirmationBody`: from `useGroupAccess` on the group screen, `useAccess`' `upcomingPlans` on the group list). Deleting an account likewise frees its seats on every pass that hasn't started yet (`delete_account`), and its own passes that aren't set up or are *Just me* are simply lost — the Account tab's Danger Zone warns about both (`describeForfeitedPasses`). **A renewing subscription is treated as if it's never cancelled**: it counts as unlocking its holder on any future date (`unlocked_on` in `schema.sql`, `isCoveredAt` in `utils/access.ts`), so a subscriber never has to take a seat on a pass starting after their next renewal, and it wins over a longer pass as the plan shown as unlocking someone (`get_my_access`'s `covering_plan`, `get_group_access`'s member cover), with no "ends early" warnings. Someone who cancels later takes that on themselves — follow this principle for anything new. `reschedule_plan` holds a new start to the same rule while the group's sponsor has no seat on the pass, and `/plan-setup` warns about it before saving. Once it has started, a seat stays with its holder for the whole plan, no matter what (so one seat can't be passed around to cover more people than paid for): leaving the group doesn't free it — they stay unlocked, and can use it in other groups — and deleting the account doesn't either (`plan_seats.user_id` goes null and the seat stays taken, shown as `deletedSeats` on `/group-plan`). Nothing releases a seat today; `released_at` is there for when something will. If the sponsor leaves or deletes their account, the plan keeps running and whoever takes over as the group's sponsor manages its seats (`can_manage_plan`; see the sponsor note above).
  - **Offline entries** are judged at their `p_created_at`, capped at 7 days back, so one typed on a plan's last evening still syncs the next morning — and failing that at `now()`, which is what lets a held entry through once everyone on it is unlocked (a plan bought or seat given after it was typed doesn't cover the moment it was typed); `create_log` checks for an already-synced retry (same `p_id`) *before* the paywall, so a lost response can't turn into a rejection.
  - **Writes only go through RPCs**: clients have no insert grant on `logs`/`log_members` (a direct insert would skip the paywall), `groups` only allows direct updates to `name, description, motive, hue, photo_url` (so nothing billing-related is client-writable), and the plan tables and `free_entry_usage` have no client grants at all. Reads go through `get_my_access` (`AccessProvider` in `use-access.tsx`) and `get_group_access` (`useGroupAccess`). `unlocked_until`, `unlocked_on`, `check_entry_access`, `can_manage_plan`, `create_plan`, `add_plan_seats`, `upgrade_plan` and `renew_test_subscriptions` are internal: execute is revoked from `public`/`anon`/`authenticated` (Supabase's default privileges grant new functions to those roles by name, so revoking from `public` alone isn't enough).
  - **Client side**, `src/utils/access.ts` mirrors the server rule (`entriesNeedUnlock`, which also counts this device's still-queued entries against the free ones) so the entry form (lock-badged tiles, "Unlock to add entries"), the group screen's access line (`GroupAccessLine` in `group/[id].tsx`), its member rows and the + button can explain it before anything is sent. `/plan-setup` (opened right after buying a Trip Pass, or later from `/plans`: group — groups that already have a plan, from `get_my_access`'s `groupsWithPlans`, are listed last, grayed out — → start, with the `DayPicker` calendar → who gets a seat, or "Set up later"; for a pass already set up it only moves the start) and `/group-plan` (who's covered, give/add seats, each confirmed in place with `ConfirmationBody`, and "Change start date" before it starts) are the modal screens for setting up passes and seats; `/plans` lists your passes still to set up or starting later (`upcomingPlans` from `get_my_access`) and every running plan you sponsor or hold a seat on (`activePlans`), and is where the Account tab's plan card goes once you have any. `/paywall` is the full-screen sales page and what every "Unlock" in the app opens (the group's + button and access line, the entry form, `/group-plan`, the Account tab's plan card — except that the in-group ones go through `useOpenUnlock`, which sends someone holding a bought Trip Pass that isn't set up yet to `/plans` instead (passing the group on, so `/plan-setup` preselects it), so they set that one up rather than buy another; and a locked viewer's + button opens `/group-plan` instead when the group's plan starts later and they have a seat on it or manage it; `groupId` preselects that group in `/plan-setup`, and `justMe=1`, from `/group-plan`'s "Unlock just me", starts it on the *Just me* size). Someone who has never had a plan (`hasHadPlan` from `get_my_access`: never bought one or held a seat) gets three swipeable pages (what the app does → "Get a Trip Pass", what one is and its advantages → pricing, with Trip Passes / Subscriptions tabs, then size for Trip Passes); everyone else, `pricingOnly=1` from `/plans` and `justMe=1` from `/group-plan`, only the pricing page. A bought Trip Pass goes on to `/plan-setup`, a subscription is done. **Only one subscription runs at a time** (cancelled ones count until they run out): `test_purchase_plan` refuses a second, and the only change is monthly → yearly, never back (`test_upgrade_subscription` / `upgradeSubscription`: the monthly ends now and a renewing yearly one starts in its place, so each keeps its own billing history and the old one moves to Former plans). On `/paywall`, someone who already has one only gets Yearly on the Subscriptions tab — the button upgrades a monthly one, or just opens a yearly one — and either way lands on their `/subscription`. While theirs is renewing, the Trip Pass tab also drops the *Just me* size (it would unlock nobody new); a cancelled one still gets it. Tapping a subscription in `/plans` opens `/subscription`: up top, one blue `PromoCard` for whatever's worth doing next — "Stay unlocked" (resume) when cancelled, "Go yearly" (upgrade, confirmed inside the card) on a running monthly one, nothing on a running yearly one — then its billing (next payment or "Unlocked until"), payment method, billing history from `get_my_access`'s `billing_dates`, and at the bottom a Manage section with only "Cancel subscription" (confirmed in place with `ConfirmationBody`), hidden once it's cancelled; the payment method and its "Change" are placeholders, since with store purchases the app never sees the card (it's whatever the Apple ID / Google account pays with). A floating diamond button on the groups tab (`PaywallButton` in `(tabs)/index.tsx`) opens it for anyone still locked while the paywall is on (`isViewerLocked` in `utils/access.ts`, shared with the nudge below); in `__DEV__` it's always shown and opens with `full=1`, which always shows all three pages. It also opens on its own for someone still locked (`src/hooks/use-paywall-nudge.ts`): every so often from the group list (`usePaywallNudge`; the wait grows 1 → 3 → 7 days, then stays weekly), and once per group when its free entries reach 5 and once at 0 (`useFreeEntriesNudge` on the group screen, with that group preselected). Never in an account's first 24 hours, never offline or on a cached-only copy of access (`isFresh` on `useAccess`), never for someone who can't buy (`canBuyPlans` in `purchases.ts`), and never for someone about to be unlocked (any `upcomingPlans`: a seat on, or sponsoring, a pass that starts later, or a bought one not set up yet). Its record is kept on the device (`offline:<userId>:paywall-nudge`); after the first nudge it opens with `pricingOnly=1`. Nothing is blocked on access that hasn't loaded yet — the server has the final say, and a rejected entry is held, not lost.
  - **The switches** (`billing_settings`, set by hand with `supabase db query`): `paywall_enabled` — while false, everyone is unlocked and all plan UI is hidden except from those who can make test purchases (`plansVisible` in `AccessProvider`); it's both the launch switch and the way back if billing ever breaks. `free_test_purchases` — while true, *every* account can "buy" plans for free, so the paywall can be tried for real before payments exist; while false, only accounts in `billing_testers` can (`can_test_purchase()`). **Currently (since 2026-09-30) the live project runs with both on**: locked people can't be on entries in a group once its 15 shared free entries are used and buys plans for free by pressing buttons.
  - **Buying**: real store purchases don't exist yet. `src/utils/purchases.ts` is the one place buying goes through: whoever `can_test_purchase` (`canTestPurchase` on the client) gets the free `test_purchase_plan`/`test_upgrade_plan` RPCs, and `setSubscriptionRenewal` cancels/resumes a test subscription through `test_set_plan_renewal` (a store one will have to send people to the store's own subscription settings). Test subscriptions renew for free until cancelled: there's no scheduler, so the internal `renew_test_subscriptions()` adds the missed terms to every lapsed renewing one (only while its sponsor could still make test purchases) at the top of `get_my_access`, `get_group_access` and `check_entry_access` — which is why those two reads are `volatile` and must stay POST RPCs (`test_add_plan_seats` still exists server-side but the app no longer uses it), everyone else `showComingSoon`. Prices are placeholders in euros (`PLAN_PRICES`/`planPrice` in `src/constants/plans.ts`), shown on `/paywall` and in `/group-plan`'s upgrade card (`PlanUpgradeCard`), which suggests the next group size up with the same end date, and can also make a 1-week Trip Pass a 2-week one (`upgrade_plan` sets the new end from the plan's start, so a Trip Pass's length can always be read back from its dates — `planPeriodOf`). Store purchases have to be granted server-side (a verified webhook calling the internal `create_plan`/`add_plan_seats`/`upgrade_plan`, idempotent on `plans.store_transaction_id`) — never by the app itself. The full plan for that (RevenueCat, products, fulfillment) is in the known gaps below.

# Known technical gotchas

- **`src/app/group/[id].tsx` is a ~3400-line single-file screen**, not split into `src/components/` the way the rest of the app is. `Avatar`, `AdminBadge`, `MemberRow`, `LogRow`, `MembersPane`, `LogsPane`, `MemberDetailOverlay`, `LogDetailOverlay`, `GroupAccessLine`, and their formatting helpers (`formatLogHeadline`, `formatSettlementDetail`, `formatOriginalCurrencyNote`, `describeGroupAccess`, `describeMemberAccess`, ...) are all private functions/components living in this one file. Check here first before assuming a group-screen component has its own file elsewhere.
- **`usePopupAnimation` exists in two places that have diverged.** `src/hooks/use-popup-animation.ts` is the shared version (used by `group-actions-menu.tsx`; also exports `POPUP_CLOSE_DURATION_MS` and `popupScaleStyle`). `src/app/group/[id].tsx` has its own inline copy for the member/log detail popups, extended with an `onClosed` completion callback — fired on actual animation finish, not a guessed duration — so the log popup can hand off to the member popup only once it has verifiably finished closing, rather than risking two native `Modal`s presented at once (which can silently drop the second one on iOS, or leave a dead touch-blocking overlay on Android). Editing one copy does not affect the other.
- **`Alert.alert` and `Share.share` are no-ops on the web build.** Don't rely on Playwright clicking through a confirm dialog on web — verify that logic via direct `curl` calls to the Supabase RPC/REST API instead, or note that it needs on-device verification.
- **`src/lib/supabase.ts` disables session persistence when `typeof window === "undefined"`.** This is required — Expo Router pre-renders the web build in Node during dev/build, and the Supabase client's auto session-recovery on construction crashes the entire process without this guard.
- **`detectSessionInUrl` is deliberately `false`.** Password recovery links (`src/app/reset-password.tsx`) and OAuth redirects (`src/app/auth-callback.tsx`, via `src/utils/oauth.ts`) both parse tokens by hand instead (the auth flow is `implicit`, so tokens arrive as a URL fragment, not a query param) — don't assume Supabase auto-handles either.
- **`getSession()` returns no session when offline with an expired access token** (supabase-js keeps it stored, but can't refresh it). `AuthProvider` falls back to reading the stored session directly (`restoreOfflineSession`, via the explicit `SUPABASE_AUTH_STORAGE_KEY` in `src/lib/supabase.ts`) and ignores `onAuthStateChange`'s `INITIAL_SESSION` event, otherwise opening the app offline more than an hour after last use would drop you to the sign-in screen. After a failed refresh, supabase-js waits a 60s cooldown before retrying, so a sync after reconnecting can lag by up to that long in this case — the `TOKEN_REFRESHED` sync trigger fires as soon as it lands. Queue flushes check `getSession()` first so nothing goes out as the anonymous role.
- **postgrest-js automatically retries failed GET requests (1s/2s/4s backoff).** Offline, a plain `.select()` takes ~7s to fail. Anything on a user-facing path that should fall back quickly offline needs `.retry(false)` (see `getRates` in `exchange-rates.ts`).
- **`metro.config.js` adds `.mjs` to `resolver.sourceExts`** — required for `@supabase/supabase-js`'s dependency chain. Don't remove it.
- **Deep-linked screens need to work with no back-stack.** `src/utils/navigation.ts`'s `goBackOrToGroups()` falls back to the group list when `router.canGoBack()` is false — use it (not a bare `router.back()`) on any screen reachable via a deep link (invite links, password reset, etc).
- **`reset-password` and `auth-callback` are intentionally ungated routes** in `src/app/_layout.tsx` (outside both `Stack.Protected` blocks) since both can be reached before the client has established its own session yet. `auth-callback` is only ever hit on web — `signInWithOAuthProvider`'s native path resolves the redirect in memory via `WebBrowser.openAuthSessionAsync` without the app ever unmounting, so there's no screen transition to gate.

# Testing / verification workflow

- **The Supabase CLI is linked to the live project** (`supabase login` + `supabase link` already done). Use `npx supabase db query --linked "..."` or `--file supabase/schema.sql` to run SQL directly — no need to relay SQL for the user to paste into the dashboard.
- **Verify features end-to-end against the real web build**, not just by reading code: start `npx expo start --web --port <unused port>`, sign up throwaway test accounts via `curl` against the Auth API, drive the UI with a scratch Playwright script, and check results via direct `curl`/`supabase db query` calls against the database. Clean up test accounts/groups/rows after.
- **Testing the paywall**: it's currently on for everyone, with free test purchases (see the switches above), so any throwaway account can be tested directly — delete its plans along with it afterwards. If it's ever switched back off for real users, don't flip `paywall_enabled` on just for a test — it would gate every real user past their free entries (and an older app build drops, rather than holds, a rejected queued entry). Instead set `paywall_enabled = true, free_entries_per_group = 1000000`, then give only the test groups `free_entry_usage` rows just below that (e.g. `used = 999997` = 3 free left) — no real group comes near the limit. Put the test sponsor in `billing_testers` so `/paywall` makes free test purchases. Afterwards restore `paywall_enabled = false, free_entries_per_group = 15` and delete the test plans/testers along with the accounts.
- Offline behavior also needs on-device verification; `docs/offline-testing-checklist.md` is the checklist to work through on TestFlight.
- Always run `npx tsc --noEmit` and `npx eslint <changed files>` after a change, before considering it done.

# Current known gaps (deliberately deferred, not oversights)

- Only the group's sponsor can demote an admin; in a group without a sponsor (no pass ever set up), an admin only loses the role by leaving or being kicked.
- Notifications are recorded and sent server-side, but **no phone can receive them yet**: push needs an EAS project id and a development/store build (see "Waiting on the Apple Developer account" below) — until then `canUsePush` is false and every notification is just marked sent with no device to go to. There's no in-app list of notifications either (the `notifications` table is readable by its owner, so one could be built). Expo push *receipts* aren't checked (only the immediate tickets), so a token that only fails at the receipt stage isn't cleaned up. No realtime updates exist.
- Offline support covers only new log entries and your own name/avatar (see the architecture note above). Creating/editing groups, settling debts, editing or deleting already-synced logs, joining, and admin actions all need a connection and just fail with a "You're offline" message. Other online-only writes (group create/update, leave, pin) still mostly just `console.warn` on failure, with no user-facing error. Offline-to-online sync only happens while the app is open (no background task).
- A signed-out person who opens an invite link loses it: `join/[id]` is behind the signed-in guard, so they're redirected to onboarding (or sign-in) and land in the app without joining. They have to open the link again after signing up. Onboarding's group step is also shown to them even though they're probably joining someone else's group (it's skippable).
- Apple sign-in's button is present on the sign-in and sign-up screens but intentionally inert — `handleOAuthPress` in `src/components/auth-form.tsx` routes it through `showComingSoon` since the Supabase Apple provider isn't configured yet. Google sign-in is fully wired and working.
- **Real payments aren't wired up yet** (see the plans note above; blocked on an Apple Developer account). What's missing:
  - Accounts and agreements: Apple Developer Program, an App Store Connect app with the Paid Apps agreement and banking/tax details, and a Google Play Console account with a payments profile.
  - Build setup: a real `app.json` identity, and EAS Build + `expo-dev-client`, since purchases need native code.
  - RevenueCat (`react-native-purchases`), using the Supabase user id as its user id.
  - Store products: Trip Pass one-time purchases for each length × size plus an extra-seat add-on per length, and one monthly and one yearly subscription (*Just me* only) in one subscription group.
  - Granting purchases: a RevenueCat webhook → Supabase Edge Function (verified with a shared secret) → `create_plan`/`add_plan_seats`. Since a Trip Pass is set up in the app after it's bought, nothing about the group has to be recorded before paying — the app waits for the not-set-up pass to show up in `upcomingPlans`, then opens `/plan-setup`. Renewals extend `ends_at`, cancelling clears `will_renew`, and refunds end the plan.
  - Screens: "Restore purchases"/"Manage subscription" on `/paywall`, and a warning before deleting an account that still has a renewing plan.
  - The renewal reminder (`subscription_renewing` in `send_scheduled_notifications`) quotes the placeholder price from `notification_subscription_price`, which mirrors `PLAN_PRICES` — switch it to the real store price.
  - Switching `free_test_purchases` off and removing the test purchase path (`test_purchase_plan`, `test_add_plan_seats`, `billing_testers`).
  - The web build can't buy at all.
- A group pass is tied to the group it was set up for. Only that group's members can get seats, a set-up pass can't be moved to another group, once it has started a seat can never be taken back or given to someone else (not even from someone who left or deleted their account), and a running Trip Pass can only be lengthened from 1 week to 2 weeks (via an upgrade) — anything longer needs a new plan once it ends.
- `settle_debt` doesn't check `p_amount` against the real balance. The app only ever settles exact balances, but a hand-made API call could record an arbitrary "settlement" even while locked.
